# Resend 邮件服务配置步骤

本文供后续接入邮件服务时使用。项目已接好 Resend，补齐环境变量并重启服务即可启用，无需额外安装依赖。

配置项与操作步骤核对日期：2026-10-26。

## 一、注册 Resend 并创建 API Key

1. 打开 [Resend](https://resend.com)，注册并登录。
2. 如果准备先测试管理员邮箱，可以用 `win121338@gmail.com` 注册 Resend。
3. 进入 [API Keys](https://resend.com/api-keys)，创建一个密钥。
4. 权限选择 **Sending access**。正式使用时，可将密钥限制到已验证的发信域名。
5. 保存创建时显示的完整密钥；密钥值之后无法再次查看。

API Key 是邮件服务的密钥，不是 Gmail 密码。直接将密钥填写到本地 `.env` 或部署平台的环境变量中，不要提交到 Git 或写入本文。

## 二、先完成本地测试

修改项目根目录的 `.env`，填写以下配置。不要只修改 `.env.example`，它是配置示例文件。

```dotenv
RESEND_API_KEY=re_这里替换成你的真实密钥
EMAIL_FROM="Artora <onboarding@resend.dev>"
BETTER_AUTH_URL=http://localhost:3000
```

- `RESEND_API_KEY`：上一步创建的密钥。
- `EMAIL_FROM`：邮件中显示的发件人名称与地址。
- `BETTER_AUTH_URL`：网站实际访问地址，用于生成验证和密码重置链接；本地使用其他端口时需要同步修改。

`onboarding@resend.dev` 仅供测试，只能向注册 Resend 账号时使用的邮箱发信。例如，使用 `win121338@gmail.com` 注册 Resend，测试收件人也应填写这个邮箱。向其他用户发信前，需要完成下文的域名验证。

## 三、重启服务并测试

1. 停止当前开发服务，然后在项目目录运行：

   ```powershell
   pnpm dev
   ```

2. 打开网站登录页，点击「忘记密码」。
3. 填写一个已在网站注册、且符合 Resend 测试收件限制的邮箱。
4. 检查收件箱和垃圾邮件文件夹。
5. 打开邮件里的重置链接，设置新密码，再使用新密码登录。
6. 在 Resend 后台的 **Emails** 中检查发送状态；前端显示请求受理，并不代表邮件已经送达。

### 现有开发账号的邮箱验证

启用邮件服务后，项目也会要求邮箱验证。此前在未配置邮件的开发环境中注册的账号，可能仍处于未验证状态。

如果登录时提示邮箱未验证，可以先使用登录页的「通过邮箱获取登录链接」功能，填写该账号邮箱，收到邮件后点击链接登录，完成邮箱验证。随后再测试密码登录和找回密码。

## 四、正式给用户发信前验证域名

需要一个你拥有、且能够修改 DNS 记录的域名。

1. 进入 Resend 的 [Domains](https://resend.com/domains) 页面。
2. 添加域名或子域名，例如 `mail.你的域名.com`。
3. 在域名的 DNS 管理后台，按 Resend 页面提供的类型、主机记录和值，添加所需验证记录。
4. 回到 Resend 发起验证，等待域名状态变为 **Verified**。
5. 将发件地址改为这个已验证域名下的地址：

   ```dotenv
   EMAIL_FROM="Artora <noreply@mail.你的域名.com>"
   ```

示例中的域名必须替换成真实域名。发件地址的域名需要与 Resend 中已验证的域名匹配，不能直接将自己的 Gmail 地址作为发件地址。

域名验证通过后，Resend 支持使用该域名下的发件地址，无需额外创建同名收件邮箱。接收用户回复则需要另外配置可收信的邮箱。

## 五、部署到线上

在实际服务器或部署平台的环境变量中配置：

```dotenv
RESEND_API_KEY=re_这里替换成你的真实密钥
EMAIL_FROM="Artora <noreply@mail.你的域名.com>"
BETTER_AUTH_URL=https://你的网站域名
```

保存后重启或重新部署应用。线上配置不会因为本地 `.env` 修改而自动同步。

使用一个真实测试账号完成「申请重置 → 收到邮件 → 打开链接 → 设置新密码 → 登录」的完整流程。确认邮件中的链接指向线上域名，而不是 `localhost`。

## 六、常见问题

| 现象                               | 检查方式                                                                                                                         |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 页面提示邮件服务未配置             | 确认实际运行环境中的 `RESEND_API_KEY` 已填写，并已重启或重新部署。                                                               |
| 测试发信返回 403                   | 使用 `onboarding@resend.dev` 时，收件人必须是注册 Resend 的邮箱；给其他人发信需要验证自己的域名。                                |
| 已填密钥，但仍发送失败             | 检查密钥是否有效、是否有发送权限、域名限制是否匹配，以及 `EMAIL_FROM` 对应域名是否已验证。                                       |
| 页面提示请求已受理，但没有邮件     | 检查该邮箱是否已在网站注册、垃圾邮件文件夹和 Resend 的 Emails 记录。认证接口会统一返回受理结果，不能据此前端提示判断邮件已投递。 |
| 邮件里的链接打不开或指向错误网站   | 检查当前环境的 `BETTER_AUTH_URL`，修改后重启或重新部署，再申请新的邮件。                                                         |
| 启用邮件后，原有账号提示邮箱未验证 | 先通过登录页的邮箱登录链接完成邮箱验证，再测试密码登录。                                                                         |

## 七、接入检查清单

- [ ] 注册 Resend 并保存发送密钥。
- [ ] 本地 `.env` 填好 `RESEND_API_KEY`、`EMAIL_FROM`、`BETTER_AUTH_URL`。
- [ ] 重启开发服务，完成本人邮箱的重置测试。
- [ ] 为正式发信域名添加 DNS 记录，并确认 Verified。
- [ ] 将 `EMAIL_FROM` 改为已验证域名下的地址。
- [ ] 在线上环境配置这三个变量并重新部署。
- [ ] 使用真实测试账号验证线上密码重置完整流程。
